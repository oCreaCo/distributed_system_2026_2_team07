# 2026-11-15 15:00 시뮬레이터 v2: 마지막 stage 파라미터 수 수정 + DP 대역폭 효율

## 바꾼 것

1. **마지막 stage 파라미터 수** (`RunSpec.params`).
   - 로그상 embedding(63.58M)은 stage 0에만 있고, 마지막 stage에는 분류 head(`HEAD_PARAMS` = 4,200,450)만 있다.
   - v1은 첫 stage와 마지막 stage 모두에 embedding을 더했다 (0941 worklog).
   - 이 값은 gradient 크기(DP 동기화)와 optimizer 작업량에 쓰인다. 계산 시간 항(f_emb, b_emb)은 그대로 두었다.
     notc 보정 데이터만으로는 stage별 계산 시간을 나눌 근거가 없기 때문이다.
2. **DP 대역폭 효율 `dp_bw_eff`** (10번째 θ).
   - DP gradient 전송(stage당 수백 MB)의 링크 대역폭에 곱하는 계수다. 파이프라인 activation(8 MB) 전송에는
     적용하지 않는다.
   - 근거:
     - NCCL 쌍 측정에서 64 MB 전송은 tc 설정 대역폭의 50–88%였다 (0858 worklog).
     - 1번만 고치면 N8_s101에서 실측이 틀어진다. DT-FM 배치는 stage 2·3 모두 0.34 Gbit/s 링크(Ireland–Seoul)로
       gradient를 보내는데, 실측 opt 단계는 37.7 s다.
       - v1(마지막 stage 366M): 35.9 s로 예측했다.
       - 파라미터만 고친 경우(306M): 30.2 s로 예측해 DT-FM 배치(78.7 s)가 찾은 배치(79.1 s)보다 빠르다고 본다.
         실측은 73.0 vs 67.2 s다.
     - 즉 v1의 "마지막 stage gradient 과대 계산"이 "실효 대역폭 과대 가정"을 우연히 상쇄하고 있었다. 둘을 함께
       고쳐야 한다.
3. **보정 데이터 확장** (`sim/fit.py` `load_inline`).
   - 11-03의 74 run에 11-15 run 46개를 더했다 (N8 s100–102 PP4×DP2 22개, calib2 24개).
   - ranking 지표는 topology × 병렬 구성 그룹 단위로 계산한다.
   - 보정 절차는 그대로(`fit_two_stage`)이고, `dp_bw_eff`는 네트워크 단계에서 함께 적합한다.

보정 결과: `dp_bw_eff` 0.940, `beta` 0.166 → 0.128, `opt_per_gparam` 13.64 → 13.48. 나머지는 사실상 그대로이고
`tcp_window_mb`는 10.1이다.

  - stage를 3종류(첫, 중간, 마지막)로 구분하고 각 stage의 gradient 크기를 따로 계산한다.
  - DP 링크에 `dp_bw_eff`를 적용한다.
  - N128을 허용한다.
- 모델 값과 시뮬레이터 예측의 차이는 1e−10 수준이고, N8_s0에서는 전수 탐색 최적값(50.208 s)과 같다.

## 시도했지만 채택하지 않은 것

모두 120 run으로 평가했다. 스크립트는 scratchpad의 `proto.py`, `wgrid.py`, `etaw.py`, `etadp.py`, `permb.py`다.

- **파이프라인 activation 전용 TCP window (W_pp)**
  - PP8의 micro-batch당 시간은 W ≈ 4–5 MB에서 잘 맞는다. 예: s305 최선 0.203 vs 실측 0.210 s, s323 최악
    0.357 vs 0.357 s.
  - 그런데 같은 W를 쓰면 PP4×DP2를 크게 과대 추정한다.

    | W_pp | PP8 MAPE | PP4 MAPE |
    |---|---|---|
    | 4 MB | 10% | 28% |
    | 11 MB | 24% | 7% |

  - 하나의 window로 PP8과 PP4를 함께 설명할 수 없다. PP8에는 다른 메커니즘이 있다는 뜻이다.
- **모든 링크에 같은 대역폭 효율 η와 window W 적용**: (W, η) 격자 30개 어디에서도 PP4 오차가 8% 아래로
  내려가지 않았다. η < 1이면 PP4를 과대 추정한다.
- **앞뒤 링크 시간 합산(`LINK_SUM`)**: PP4를 40–100% 과대 추정한다.
- **메시지마다 RTT 오버헤드 추가**: 2–3배 과대 추정한다.
- **rank 0의 fwd 단계로 직접 적합**: PP4·PP2에서는 rank 0(stage 0)의 fwd 단계가 하류의 병목을 반영하지 않는다.
  그래서 이 지표로는 적합이 의미가 없다. `fit_two_stage`의 breakdown 잔차도 같은 문제를 갖는다 (가중치 0.5).
  이 부분은 고치지 않았다.
