# [2026-11-15 05:20] N=64 개선 시도: 개선 없음, 대신 정확한 최적값으로 headroom 측정

두 번째 Claude Code 에이전트(약 21분). 목표는 새 N64 topology dev set(seed 6000–6019, `adrs/dtfm_placement/dev_eval.py`)에서
현재 최고 프로그램(`output/agent_cc/best_program.py`)을 넘는 것. 작업 폴더는 `output/agent_cc2/`.

## 결과
- **개선 없음.** 납품한 `agent_cc2/best_program.py`는 baseline과 바이트 단위로 같다.
  - train 1.27772, 실패 0.
  - 유일한 dev 실행(v2)은 0.99875(3개 나빠짐)였다.
  - v2의 변경 내용으로는 그 3개가 나빠질 수 없어서 실행 간 편차로 본다. baseline이 시간 제한(30 s) 근처에서 멈추는 topology가 있다.
  - 단일 topology 편차는 앞서 잰 ±0.0005보다 크다.

## 핵심 발견: N=64 정확한 최적값 (`agent_cc2/study/exact.py`)
- 목적함수는 두 임계값으로만 정해진다.
  - C: 쓰인 파이프라인 링크 중 가장 느린 것.
  - D: stage별 hub까지 가장 느린 gradient 링크.
- 이 구조로 (C, D) 계단을 따라가며 scipy MILP(HiGHS)로 실현 가능성을 확인해 최적 배치를 구한다.
  - 대상은 seed 1000–1059(연구용 범위)다.
  - 구한 배치의 시뮬레이터 값은 `REF.predict`와 1e-9까지 일치한다.
- 내가 독립적으로 다시 확인한 것:
  - 60개 모두 유효한 순열이다.
  - 예측값이 보고한 최적값과 같다.
  - baseline보다 나쁜 경우가 없다.
  - baseline/최적 기하평균은 1.0029다.

| | 값 |
|---|---|
| baseline이 최적과 같은 topology | **55 / 60** |
| baseline / 최적 (기하평균) | **1.0029** (0.3%) |
| 최적을 놓친 5개 | 1005 +6.1%, 1027 +5.8%, 1044 +3.0%, 1045 +2.1%, 1007 +0.7% (모두 지역 7–8개) |
| MILP 시간 초과가 있었던 seed | 1005, 1027, 1037, 1054. 이 4개는 최적이 증명되지 않았고, 진짜 최적이 더 낮을 수 있다 |

- 놓친 경우의 원인은 실현 가능한 배치를 찾지 못한 데 있다(4/5는 C가 같고 D가 더 작은 배치가 존재).
  - 그 임계값에서 실현 가능한 배치를 local search(annealing 여러 변형, warm start)로는 거의 못 찾았다.
  - 열 단위 정확 탐색은 상태 수가 폭발해(seed 1005에서 2열째에 0.9M) 순수 Python 30 s 안에는 불가능했다.
  - 프로그램은 표준 라이브러리만 써야 해서 MILP를 쓸 수 없다.

## 결론
- **N=64에서 남은 headroom은 약 0.3%(기하평균)**이고, 지역이 7–8개인 어려운 topology 몇 개에 몰려 있다.
- 앞의 결과와 합치면, 이 시뮬레이터와 예산에서 **배치 품질은 사실상 최적에 도달**했다.
  - N8은 전수 탐색 최적값이다.
  - N16–N32는 여러 탐색이 같은 값에 도달한다.
  - N64는 MILP 최적과 55/60이 같다.
- 남은 개선 여지는 배치 탐색보다 **시뮬레이터 자체의 정확도**에 있다.
  - A100에서 8–21% 과대 추정했다.
  - 파이프라인 방향을 구분하지 못한다.
- 주의: 이 결론은 시뮬레이터의 최적이다. 실제 하드웨어의 최적과는 시뮬레이터 오차만큼 다를 수 있다.
